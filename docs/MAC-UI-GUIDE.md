# Daedalus for macOS — native Fluent UI preview guide

**Status:** implementation preview; not production/real-account acceptance. The sole active OpenSpec change `finish-v010-engineering` tracks remaining automated QA and engineering; physical Mac acceptance is separate. This guide describes the preview build generated by the `Native macOS app preview` GitHub workflow for the relevant revision, not an existing installed copy.

## Obtain and open the preview

1. Open the [implementation PR](https://github.com/itshak/Daedalus/pull/63) and select **Checks**. Find the successful **Native macOS app preview** workflow run; download its Daedalus app ZIP under **Artifacts**. Artifacts may require signing in to GitHub and expire according to GitHub retention policy.
2. Unzip the `Daedalus.app` archive on the Mac. The workflow labels this an ad-hoc signed preview, **not Apple-notarized release software**; macOS may display a Gatekeeper warning. Follow your security policy for software from source-controlled previews. Do not disable system-wide Gatekeeper.
3. A source-based alternative is to install Python 3.11+, clone the exact reviewed revision, run `python -m pip install -e ".[desktop]"`, then `daedalus-desktop`. This does not install an Apple-notarized app.
4. To explore without Gameforge, open Connection and choose **Try offline demo** under Advanced connection options. Demo is explicitly labeled SYNTHETIC DEMO and cannot modify game state.

## Navigation and connection

Primary navigation: **Overview** (account and action cards), **Accounts** (session status, sign-in and editing), **Warehouses** (all-account reports and printing), **Automations** (discover/configure, running, history, all-account status), **Activity** (local sanitized events). Bottom utilities: **Connection** (link symbol) and **Settings** (gear). Wine and Construction are Automations shortcuts, not separate competing task editors.

Connect to an approved Daedalus backend using a trusted HTTPS URL and the **Daedalus API bearer** in Connection; this is not the Gameforge account password or Gameforge session token. With the default secure save preference the bearer is stored only in the OS Keychain under the **exact approved HTTPS origin**, with auto-reconnection on later launches. Use a one-time ephemeral connection by opting out. SSH is an advanced fallback, not a requirement for normal Mac usage.

A connected backend is necessary for actual account snapshots. The desktop does not automatically start or resume game tasks after connection. The Mac may close while server-owned workers continue independently.

## All-account warehouses — primary reporting workflow

**You do not need to visit each account separately.**

1. Open **Warehouses** and click **All accounts**. The GUI requests read-only warehouse snapshots for every configured account, combining successful city rows into a single table. Accounts without authenticated sessions appear as unavailable; missing amounts are **unknown**, never falsely zero.
2. Optionally use **Only 220K+** for cities meeting the existing unsecured total threshold and **Group by island** to keep same-island cities together.
3. Click **Print report…** to preview and print the current combined text report using the macOS print dialog. The preview reflects current filters and selected island grouping. You can also choose **Export report** for Copy CSV, Copy grouped island text, Save CSV, Save JSON or Save TXT.
4. To limit the report, click **Choose accounts…**, select any group and choose **Use selected accounts**, then **Selected (N)**. The selected accounts are remembered as nonsecret, per-backend report preferences. **This account** provides the legacy focused view.
5. If a snapshot is unavailable or a partial refresh fails, the status line identifies it; do not interpret the absence of a city as a zero resource amount. You can refresh read-only reporting safely.

All-account reports and read-only task status include **every configured account**, without silently discarding accounts after the first 100. Large account lists may take longer to query sequentially, and individual errors appear as unavailable rather than false zero values. Read-only reporting does not start, stop or interfere with game operations.

## All and selected account automations

Open **Automations**. The single Fluent workspace separates **Configure**, **Running**, **History & recovery**, **All accounts**, and the embedded **Catalog**. Wine and Construction shortcuts change the filter inside this same workspace; they do not open separate editors or retain conflicting drafts.

- **View all task statuses** queries each configured account (including disabled ones) and displays running count, unresolved request count, and unavailable account status. **Choose accounts…** followed by **View selected statuses** checks just the chosen group. These are read-only requests.
- In **Discover & configure**, use Search, Category or Wine/Construction shortcuts to find a registered task. Tasks only appear executable if the backend advertises guarded dispatch. Known fields are ordinary controls; complex schema fields may still require Advanced JSON in this preview.
- A **single-account Start** requires passing backend preflight, a reviewed configuration, an explicit approval checkbox and a separate confirmation dialog.
- **Start for selected (N)…** is available only for a selection of 1–32 enabled accounts; disabled accounts remain included for read-only status. It is an advanced group action and can change game state on multiple independently owned accounts. Review the exact names, task and settings. The worker checks all accounts' prerequisites before starting any; one blocked account blocks the cohort. Each approved account gets its own unique authenticated request. If one start result is uncertain, the process **halts without retrying** or silently treating the request as successful. Review the account's request history and game state before further action.
- The **Running** section retains per-account managed-task Stop with separate confirmation. The **History & recovery** section retains manual reconciliation for an unconfirmed request. Never press reconciliation merely to clear a warning without independent checks.

The user interface does not bypass backend permissions, task leases, idempotency, game engine validation or CAPTCHA. Multi-account task starts are intended for deliberate operator-authorized use, not automatic unattended all-account launch.

## Automatic headless Gameforge sign-in (the prior warehouse-bot workflow)

**The normal path is now automatic Selenium Chrome, not a manual Gameforge browser.**
This is adapted from the original local warehouse bot in
[itshak/ikabot](https://github.com/itshak/ikabot): restore the previously saved
world session when available, otherwise enter Gameforge lobby using stored
email/password, select the game's play/world entry, and detect the exact-world
authenticated city UI. Selenium starts with **headless Chrome**. A visible
Chrome window is opened **only when an actual CAPTCHA is detected**, so the user
can solve it; Selenium resumes navigation itself. A wrong password, missing
browser, timeout or world mismatch does *not* open a random visible browser.
CAPTCHA is never solved or bypassed by software.

In Daedalus **Accounts**, select **Sign in automatically (headless)**, **Sign in
all accounts**, or **Choose sign-in accounts…**. The **Warehouses → All accounts**
button also checks which accounts lack verified sessions and attempts headless
sign-in for those accounts before collecting **one combined warehouse report**.
Already authenticated accounts require no new login. Existing island grouping,
220K filter, native Print preview and CSV/JSON/TXT exports remain unchanged.
All attempts are account-scoped, proceed sequentially and report errors
independently rather than aborting a full multi-account report.

On the first use, Daedalus tries an exact account alias match in the previous
local bot's owner-owned `~/.ikabot/config.ini` and an unexpired, exact-world
session in `~/.ikabot/tokens.json`. Neither source is changed or copied into
Daedalus settings. Otherwise you supply your Gameforge email/password **once**
through a secure Mac form, and can save them to **macOS Keychain**, bound to
the exact backend HTTPS origin, account ID and world. Subsequently those
credentials are reused automatically and no password input is needed until
they are unavailable or changed. They never leave the Mac for the Daedalus API.

After login, the Mac extracts **only the exact world's secure `ikariam`
cookie** and uses the existing single-use, account/world/player-bound
X25519/AES-GCM handoff. The authoritative backend independently verifies the
game identity, respects active task/uncertain-request ownership and accepts
or rejects the new session. It does not start game tasks. For emergencies,
**Manual browser fallback** is available under Advanced recovery; it is not
the ordinary sign-in flow.

**Scope and acceptance:** This requires a trusted HTTPS Daedalus connection,
backend native browser handoff enabled, Chrome/Selenium on the Mac and
account-scoped Gameforge credentials or a matching legacy configuration.
Source code and synthetic tests do not establish that a live Gameforge
CAPTCHA, 2FA prompt or world selection currently succeeds. The owner will
perform actual account tests separately; no live credentials or game traffic
were used during implementation.

## Accounts and sign-in

The Accounts table summarizes each account and its worker state. Choose an account to see contextual health and **Sign in automatically (headless)** when the backend enables secure browser handoff. Selenium fills the login and opens visible Chrome only if CAPTCHA requires your intervention, then uses the one-use encrypted, account-bound handoff. The backend independently verifies the exact world/player before accepting the result. Browser acknowledgment alone is **not authentication**.

Account editing is permitted only when the controller enables its protected metadata editing mode. More technical monitoring, manual assistance and host recovery actions are under **Advanced recovery and monitoring**. Their per-account security confirmations remain mandatory; multi-account sign-in proceeds one account at a time and cannot start tasks or bypass server ownership.

## Appearance, layout and diagnostics

Settings controls theme (System/Light/Dark), default warehouse filters and secure connection shortcut. Activity provides bounded local desktop diagnostics; it is **not** a complete remote historical audit feed. The GUI uses the existing Fluent widgets and Mac-native titlebar treatment, and all HTTP access runs off the Qt GUI thread.

## Known preview limitations and testing requested

- Automated visual and accessibility QA is tracked in the engineering successor; physical Mac/VoiceOver and release UX review are deferred to [owner acceptance](V010-OWNER-ACCEPTANCE.md).
- The Mac app preview is ad-hoc signed and may trigger Gatekeeper; **not** Apple-notarized. Do not equate preview packaging success with live production acceptance.
- Owner-only real Mac Gameforge/MFA/CAPTCHA login, independent recovery, reboot persistence, and game task effects remain tracked in [issue #60](https://github.com/itshak/Daedalus/issues/60). No public CI job executes real-game operations.
- Test in synthetic demo first. When you authorize a real workflow, begin with **read-only All accounts warehouses** and Print preview. Report only sanitized status/errors, not tokens, cookies, private account files or session logs.

## Account scope by screen

The title-bar **Account scope** control is the shared working context. Choose
all accounts dynamically, one player or an explicit subset; clear all
checkboxes and accept to choose none. The preference is local to the
connected backend. All scoped screens receive the same effective authorized
roster. Account-specific selectors refine that roster, never expand it.
Changing scope clears old reports and task reviews, but does not stop
running game tasks.

| Screen | Working context |
| --- | --- |
| Overview | Scoped account cards and session summaries |
| Accounts | Scoped account table; explicit **Manage all accounts** for administration |
| Warehouses | All/selected/single within the working scope; existing combined exports |
| Automations | Scoped enabled execution targets and scoped status targets; one eligible account is automatic |
| Military | Scoped inventories and movements |
| Activity | Scoped server receipts; untagged local diagnostic events remain application-wide |
| Settings | Global appearance and connection; account-specific administrative controls are scoped |

## Redesign follow-up: guided discovery and scope continuity

The Overview now presents independent backend-derived summaries for **session
verification**, **warehouse reports**, and **task status**. Reports or task
statuses that have not been read yet say *Not checked*; an account that failed
to load is *Unavailable*, not zero. Switching to a different backend origin
clears the prior backend's account and task draft context before new data is
rendered.

The Automations **Discover & configure** view has a searchable Fluent card
gallery with semantic icons populated exclusively from the connected engine registry. Choosing
**Configure** selects the associated task, never starts it. Category and
search filters apply to both the gallery and complete selector; complex plans
still require reviewed input or Advanced JSON when backend metadata lacks
safe choices. **Running** and **History** now have explicit account
selectors and a shortcut to **All account statuses**. Routine tables use
human-readable status; select **Task details** or **Request details** for
managed IDs and process/request identifiers. Stop only targets an authorized,
running, backend-managed task; uncertain requests never retry themselves. Every multi-account start consent names **all** selected account labels, worlds and IDs, including groups larger than 12.

Settings includes a working-scope summary and shortcuts to the same shell
selection. These choices are local UI preferences scoped to the connected
backend; they do not change account enablement or grant authorization. Connection displays
explicit in-progress feedback and sanitized guidance for rejected tokens,
untrusted TLS, unreachable servers and unavailable Keychain. Authentication uses **Sign in automatically (headless)** for one, all or selected accounts and can run from warehouse refresh when a session is missing. The older manual browser remains an Advanced fallback.

## Navigation and keyboard shortcuts

The Mac window supports **Cmd+,** for Settings, **Cmd+R** for a safe read-only refresh of the active Overview, Accounts, Warehouses or Automations screen, and **Cmd+F** to focus Automation search. Refresh never launches or reconciles a game operation. At the supported minimum window size (900×650 logical pixels), forms and Settings scroll vertically; Accounts uses a resizable list/detail splitter.

## Guided automation form behavior

The editor uses backend-advertised field types and defaults. A dropdown is shown only when the backend explicitly supplies a bounded list of permitted choices; Daedalus never guesses city IDs, game targets or enum values. Known Wine, Construction, alert, piracy and resource fields have task-specific help and units where source-reviewed. Required complex arrays/plans remain **Advanced structured input** until the engine advertises sufficient metadata to construct them safely. Do not invent game data merely to avoid JSON.

The review checkbox is invalidated when the account, task, field values or imported JSON change. The separate review confirmation shows the account, task and safe settings summary. The Start action is blocked while its prior request is pending, including after double-clicks; an uncertain response must be inspected through History and is never retried automatically.

## Activity and account workspace

Accounts presents a resizable master/detail view: choose an account on the left and see the current verified status, contextual login and permitted metadata/recovery actions on the right. **All accounts** still includes disabled accounts for read-only warehouse/status views, while mutating tasks require enabled accounts and explicit consent.

Activity is a filtered local timeline with generic nonsecret event descriptions. Filter by severity and event type; individual account filtering is unavailable because the local events are not reliably account-attributed. Select **Show advanced diagnostics** to inspect bounded technical client logs. Neither view is an authoritative server audit trail; use Automations → History to inspect request receipts and uncertain launches.
