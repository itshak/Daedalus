# Production workforce policy
## Existing engine
modifyProduction.py already provides _read_worker_slider, _submit_worker_assignment, preview_native_workers and reviewed execution. Current slider exposes max_value, overcharge, optional value; current target is normal percentage plus full extra capacity at 100%. Audit pinned upstream and actual authoritative population/slider fields before claiming any more capabilities. Reuse those helpers and original request construction, no independent game client. Exact normal/extra targets map to one total only if the actual game enforces normal-first allocation; reject unrepresentable combinations and unknown capacities. Extra workers means overcharge; do not infer a separate independently configurable pool.
## UI and scope
Production screen supports per-city actual resource, normal/extra capacity/current when observed, citizens and hourly production/cost only when authoritative. Wood, wine, marble, crystal, sulfur, all; filter luxury sites by verified resource identity rather than city name. One/selected/all accounts, per-city exclusion and overrides; preview exact immutable city/project pairs. Maximum uses each city's actual capacity, including optional full overcharge. All resources has no implicit competing priority: require explicit ordering or a reviewed non-reallocation allocation when population is insufficient. Academy and temple remain separate workforce sections; never raid scientists, priests, military, other cities or accounts to fund production. No new writes from view/filter changes.
## Default priority policy (owner decision)
Checkbox label "Use only available population", default unchecked. Unchecked means prioritize selected resource, including requested overcharge. First use free citizens; if insufficient, release the minimum necessary workers from the other resource production site of the SAME city (wood for a selected luxury site; luxury for selected wood). Keep donor at its original allocation if possible, and restore unused released citizens up to original donor allocation, subject to fresh capacity and available population. Do not raise donor above its reviewed original allocation. If both sites cannot be full, selected site wins. Checked means never reduce other site; set maximum feasible target using only currently available citizens and current target-site workers. Existing target-site workforce counts toward target, not a second demand for citizens. If insufficient even after donor is emptied, set highest feasible target, report shortfall. Never touch a different resource/city than explicitly reviewed except the identified donor site. Lowering targets does not implicitly increase another site above its original allocation.
Example: crystal current 400, target 900 (750 normal + 150 overcharge), free 200, wood current 700. Release 300 wood workers, verify, set crystal 900, wood 400. If free/maximum cannot be known exactly, use a separately disclosed staged fallback (enabled by default for single-resource planning, still subject to explicit preview approval): snapshot both allocations and approved donor floor of zero; release all donor workers only when necessary and explicitly included in the reviewed plan; refresh authoritative slider/population; maximize target with existing helper, then restore surplus to donor up to initial count. If game cannot reliably identify current allocations or confirm writes/readback, block rather than blindly empty donor. Do not silently treat unknown as zero.
## Safe staged execution
Preflight reads ownership, site identity, both allocations, capacity, free citizens and target feasibility. Review shows before/after target AND donor, maximum displacement, exact vs fallback, shortfalls, affected city count and disconnected/excluded accounts. Server validates policy, target and donor identities, fresh plan and approval, no stale or arbitrary game request. Serialize per account/city with existing ownership/session lock. Use durable per-city staged intent/receipt: initial snapshot, intended absolute targets, release pending/confirmed, target pending/confirmed, donor restore pending/confirmed, terminal or needs review. Before each mutation re-read state, validate current step and ownership; use shared assignment helper with no ambiguous retry. Verify actual assignment via readback, not mere request acceptance. Persist pending before any mutation; no unconditional replay of uncertain writes. If confirmed release but the existing mutation adapter proves the target was not submitted, or authoritative evidence proves rejection, record the refusal and restore the original donor safely if still valid and within approved bounds; if partial target succeeds, restore all feasible unused workers without undoing verified target. If timeout/crash/session loss/external changes, reconcile both sites against journal and fresh observations; if uncertain hold needs review, show actual/last known allocations and actionable recovery, never blindly replay release or restore. Preserve progress and partial results; do not claim success until observed. Explicit stop prevents subsequent writes except separately authorized safe compensation. Keep existing reviewed one-site operation backwards compatible.
## Bulk behavior
Group per-account execution through current reviewed controller, bounded sequential work within each account, isolate errors, report each city independently, never silently include an account or nonmatching resource. No rollback of unrelated successful cities. Global confirmation requires counts and donor impacts. Idempotency and fixed account/city target set; no unbounded fanout. Web and Mac parity, EN/RU web. No gameplay mutation during planning or synthetic tests.

The implemented definitive evidence is limited to a typed local pre-POST refusal. No unverified workerPlan server feedback type is interpreted as rejection. Live server response semantics remain an explicit acceptance gate.
