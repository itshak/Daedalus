# Design — local OS-keyring world cookie handoff

The operator manually completes any login/CAPTCHA in their own trusted browser. In a local interactive terminal, with a configured account ID and canonical world/player, they confirm one read-only game-world verification and privately paste only the `ikariam` world cookie via `getpass` (terminal echo disabled). The CLI refuses non-TTY sessions to prevent accidental plaintext capture.

The Daedalus saved-user email binding remains in the OS keyring, not in `accounts.toml`. A separate keyring service stores the verified game-world cookie under a SHA-256 digest of account ID, world and player, so changing identity invalidates the binding. No cookie is placed in the controller API, environment, shell arguments, project files or logs. A missing/unsafe OS credential backend fails closed with no plaintext fallback.

Import validates the cookie format, obtains the host-local world/player lease and invokes an in-memory cookie-only IkaBot restoration. The engine accepts `world_cookie_override` only when `cookies_only=True`, never invokes lobby/blackbox/loginLink, substitutes the value into a temporary world-specific cookie jar and validates the world response and exact saved player selector. The current world HTML marker does not independently attest server-side player identity; production use requires a separate verified identity signal. The temporary HTTP session is closed and the lease released in both success and error paths. Only after success is the cookie placed in OS keyring. A failed re-import leaves the previous verified cookie untouched.

Future `probe-saved-cookies` commands may look up this override and repeat the same guarded validation. The normal engine's unaided upstream CLI semantics remain unchanged. Importing a cookie does not update a separately running IkaBot process or automatically reopen a game worker. The user must stop conflicting sessions and use a separate trusted engine restoration path when available.
