# Warehouse-fill recovery
Inspect actual fillCityWarehouse preview, reviewed_sources, _WarehousePolicy, upstream executeRoutes/sendGoods, fixed-transfer write-ahead journal and recovery allowlist. The current operation is one-time with reviewed source caps, not an unrestricted ongoing replenishment policy. Preserve original approved destination, resource, fleet, account ownership, per-source caps and limits; never silently approve new sources or replenished quantities. Add durable per-chunk pending/accepted/rejected/uncertain receipts at shared upstream submission boundary as needed, prefer existing fixed-transfer primitives and no extra game networking. Fresh destination stock, free space, reliable incoming cargo, source stock, fleet and confirmed remaining per-source allocations constrain restored plan. Guard against double counting stock and in-transit cargo, changed identity and concurrent dispatch. Pending or conflicting receipts, missing historical progress, stale ownership or unreliable incoming data block automatic resume; preserve manual status for legacy jobs without trustworthy journal, no retroactive inference from cumulative counters. Completed only with evidence that approved capacity/intent exhausted; insufficient stock distinct from complete. Restart policy default on for newly approved qualifying jobs; existing disabled/pause/stop/epoch/idempotency fences unchanged. Both server startup and session reconnection restore only after authenticated account and existing task/receipt reconciliation; confirm startup trigger as separate regression. Expose operation recovery class and reason prelaunch, actual held/eligible state in existing UI; telemetry redesign can consume later. Tests simulate waiting, accepted ship, crash before/after acknowledgement, delivery while offline, stale/ambiguous cargo, ownership, no fleet, multiple restarts and stop, synthetic fixtures and owner acceptance separately.
