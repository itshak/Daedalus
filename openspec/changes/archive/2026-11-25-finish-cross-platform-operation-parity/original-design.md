# Design

## Architecture and ownership
Use the current PySide6/QFluent desktop and Next.js/React web shell; retain Supabase authentication and server-only HTTPS BFF. Backend owns versioned per-operation manifests: canonical name, category, supported scopes, platform policy, required inventory providers, typed draft schema/version, preview/execute strategy, risk, preflight requirements, receipt/recovery semantics and localization keys. Generate Python and TypeScript contract fixtures/types from one reviewed schema source. UI rendering is native/domain-specific, not an AST-derived generic form. A manifest can describe a primitive editor but opaque engine structs are generated only by validated adapters. Keep legacy task API compatibility where safe; migrate callers incrementally and remove raw editor bypasses. Never trust a browser-provided player, city, cost, role, preview or arbitrary engine config.

Proposed read endpoints: operation manifest, scoped city/island/destination search, inventory and current state. Proposed operation-specific draft endpoints accept typed inputs only; authoritative read-only prepare/preview returns normalized human-readable effects, cost/ETA when available, warnings, immutable scope and short-lived opaque preview ID/fingerprint/revision. Execute accepts operation, account, approved preview token (or validated typed primitive draft for simple operations), explicit approval and unique request ID; backend revalidates live scope, permissions, game session, staleness and prerequisites before invoking the engine. No preview may mutate the game. Exact path naming is an implementation decision; document OpenAPI and generate contract tests before frontend wiring. For synchronous settings/one-shot actions, return durable receipt or explicit uncertain outcome rather than pretending all operations are background tasks. Reuse existing managed task IDs, ledgers and restoration policies, never restart a completed one-shot action or guess remaining quantities.

## Native interaction model
Desktop: compact Fluent account toolbar; grouped search and a single context form; real names, native combobox/checklist/spinbox/time/date controls, game icons and tables, scrollable content with visible review footer. Web: same category, account names, field semantics and validation using responsive React controls, accessible search/combobox, editable tables, sticky review footer, mobile-friendly route cards and progressive disclosure of *native* optional settings only. Keep English/Russian i18n and light/dark design; use existing game resource assets. Never label a read-only generic data table as a configurable workflow. No JSON editor/import, raw ID entry, or unstructured configuration textbox; ordinary text fields for human names/hostnames remain valid. No fake values in disconnected state.

Transport: choose actual origin and destination cities by name; support own city list, verified external island/player/city search where upstream allows, prevent same-city/unauthorized/stale cross-account routes; show five resource icons and integer quantities, fleet mode, observed stock/ships/capacity, ETA if verifiable, repeat schedule. Construction: multiple ordered upgrades, valid targets, costs and shortages, supported supply routing, queue duration and review. Training/trade/faith/research/production use real choices and typed amounts. Matrix defines every operation's domain UI and implementation gap. Provide useful loading/empty/error/stale states and explicit reasons for unavailable actions.

Account scope: actual game player name first, meaningful configured fallback, duplicate disambiguation by world and stable ID; email remains on account management when appropriate. Current/selected/all are first-class; only supported operations batch. A batch creates distinct scoped drafts/previews per account, never broadcasts one city's IDs; show each account's effects and eligibility, exclude/resolve blocked accounts explicitly, respect existing limits, stop on uncertain dispatch; no silent partial success. Changing account, operation, inventory, fields or preview invalidates review. Reconnect restoration remains backend-owned with durable progress/receipts.

## Security and exceptional functionality
Interactive-only functions need dedicated adapters, allowlisted paths and DTOs. Web BFF validates session, role and account scope, origin/CSRF, strict per-operation schemas and bounded body/response; server-only bearer, no-store, rate limits, redacted errors. Desktop respects same controller policy. Native browser login/session export and local secret handling remain protected; browser can show status and guided local handoff, not session material. Admin settings use write-only masked secret fields, explicit roles, audit, and approved management interfaces. Developer/extensions/updater never become arbitrary remote execution; offer reviewed signed/trusted extension enablement and controlled release management. If upstream feature cannot safely cross a trust boundary, record a security-equivalent local/admin workflow and owner-approved exception, not generic JSON or an endless disabled placeholder. Read-only features need no mutation path.

## Parallel delivery
Wave 0 shared schema, inventory coverage test and representative contract fixtures. Track A backend/engine supplies reviewed per-domain adapters and tests; Track B desktop implements Qt editors using fixtures; Track C web implements matching React editors and BFF strict policy using same fixtures. Each domain vertical slice integrates all three; independent worktrees/PRs avoid conflicting files, interface changes require contract version update. Do transport and construction first, then cities/research/faith, trade/military, monitoring, interactive/admin. Existing desktop forms are reused and refactored only as needed; PR #95 is prerequisite or reconciled before implementation. Merge small green slices, never mark parity complete until every registry row has both supported workflow evidence or approved boundary exception. Release backend compatibility first, then web deployment and desktop DMG; verify actual deployed versions and rollback plan. Live acceptance is owner-operated, not automated game mutation.

## Test and completion model
Machine-readable operation coverage checked against inspect_engine() plus interactive submenu inventory, per-platform editor route, capabilities, fixture, validation and tests. Unknown/missing registry action fails CI; no raw config UI anywhere (including advanced mode). Contract tests enforce no unknown keys, account mismatch, stale/expired previews, permissions and no side effects. Qt offscreen and native macOS checks; web unit/typecheck/build plus Playwright for every operation family, responsive and accessibility states. Test account switch, duplicate names, real option binding, validation, no consent, success receipt, uncertain outcome, stop/recovery, and batch isolation. Synthetic fixtures must be labelled and never touch real accounts. Verify actual live data and actions with owner before declaring release acceptance. Keep checklist unchecked until evidence exists.
