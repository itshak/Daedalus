# Durable logical task monitoring

## 1. Existing architecture and boundaries
TaskController and TaskLedger (src/daedalus/task_control.py) govern dispatch/stop and authoritative receipts; RecoveryStore (recovery_state.py) governs desired jobs and resume receipts; recovery_reconcile.py defines safe restart classes. Engine IPC is the account-bound execution boundary. fillProgress.py provides volatile stage/submitted/verified counters; engine_ipc.py validates these. activity_history.py and the web activity-history component expose receipt history, not proof of game effects. Preserve these authorities. Telemetry is observational, never an executor or a recovery authorization. Follow ADR-006; inspect upstream first, prefer existing hooks or narrow observational extraction, and test parity.

## 2. Logical identity and data model
Use a separate private SQLite telemetry database, owner-only directory/file, versioned additive schema and transactional append/projection. Do not duplicate task-control/recovery authority.
- logical_tasks: opaque logical_task_id, account/world/player identity binding, operation, approved_at, sanitized reviewed configuration projection, receipt reference, desired-job reference if present, optional batch correlation, metric schema version, telemetry coverage. Every new approved manual task gets a new identity, even if configuration is identical.
- execution_runs: run_id, logical_task_id, account binding, engine registration ID, controller generation, recovery epoch, attempt sequence, lifecycle timestamps, status/evidence, outcome. PID is diagnostic only. Unique recovery-run binding and request correlation. Batch account children remain distinct.
- activity_events: event_id, run_id, logical_task_id, run sequence, observed_at UTC, optional occurrence time, type/version, operation correlation, typed safe payload and evidence grade. Unique event ID and (run_id, sequence); deterministic projection ordering; reject mismatched account/run and conflicting duplicate.
- metric_projections: logical_task_id, metric/version, per-resource/per-unit totals at distinct evidence levels, counts, durations, completeness, last observed, checkpoint.
- retention_checkpoints: retained event watermark, cumulative rollup, truncation/coverage flag. Keep totals after pruning old detail; never imply full timeline when truncated.

Link logical IDs at the reviewed launch/receipt boundary, then associate engine registration. Pending and uncertain launches remain visible as such. On a genuinely authorized restoration, use the existing desired-job ID and recovery epoch/receipt to associate a new run with the same logical task. Never infer linkage from PID, player name or matching task text. Record gaps for old or missing identities. No telemetry database restoration may trigger game execution.

## 3. Event production and reliability
Controller emits lifecycle observations from existing dispatch, stop and recovery transitions. Engine emits typed events at existing response and wait boundaries. Reuse upstream sendResources/executeRoutes/sendGoods and waitForArrival/getMinimumWaitingTime; verify actual pinned helpers for other operations. No new game requests for telemetry; consume existing observations only. Use bounded nonblocking IPC or local durable handoff, identity-bound messages, queue limits, explicit gap counters and bounded payload. Never delay game dispatch or alter success/failure/retry decisions because an event was lost. Ingestion validates schema, correlation, sequence and limits, then atomically inserts and updates projection. Duplicate replay is a no-op; conflicting replay or missing sequence becomes incomplete/attention. Reconnect starts new run sequence, not a reset of logical totals. If persistence fails, expose telemetry degradation and unknown metrics; execution/reconciliation still obey their existing safety gates.

Transport events: reviewed target/route, source/destination city IDs and safe names when observed, resource vector, fleet kind, wait entered/exited, shipment submitted, explicit acknowledgement/verified dispatch, rejected, uncertain, observed arrival if supported. Correlate multiple observations of one shipment, count once. Accepted-but-unobserved-arrival is not delivered. Existing fixed-transfer receipts are authoritative for recovery; telemetry never substitutes for them. Waiting duration uses bounded timestamp intervals, monotonic within run and persisted UTC across runs; do not invent downtime or infer a wait ended after crash. A missing wait endpoint remains unknown. Runtime elapsed from first start; active, waiting and disconnected durations separately, excluding overlap; wall clock changes handled explicitly. Historical snapshots cannot fabricate individual shipment events.

## 4. Metric registry and coverage
Create versioned registry keyed by actual operation names from engine_registry and docs/operation-coverage.json. Every operation declares events, units, aggregation, denominator, evidence, unavailable reason and supported clients. Common: start, elapsed, observed active/wait/downtime, run count, last update, outcomes/errors/recovery (redacted). Domain:
- fillCityWarehouse/sendResources/transport/consolidate/distribute: requested if fixed, submitted/verified dispatch/delivered separately, five-resource vector, distinct accepted shipment count, source/destination, remaining only for reliable fixed targets or fresh observed capacity, throughput with stated elapsed denominator.
- trainArmy: per-unit ordered/accepted/trained only with observed completion, batches, target and remaining, queue waiting. UpgradeUnits: upgrade type/level, cost and queue.
- constructionList/constructBuilding/reorganize: slot/building, planned/current/target level, accepted starts, observed completions, cost and remaining. Research/academy: research identity, points where observed, started/completed, cooldown. Donation/donationBot: project/island, accepted wood, count. Tavern/production/temple: cities, observed previous/new allocation, wine consumption if observed. Miracle/shrine: activation and observed cooldown. Trade: confirmed orders/quantities/gold, no speculative fills. Missions: observed orders/results, no invented outcome. Alerts/monitoring/reports: checks, alerts, duration, failures, observed result count. Protected-local/unsupported functions: lifecycle only or unavailable, no new remote capability.
Never claim trained from order, upgraded from queued, delivered from dispatch, cost from preview, or exact shipments from a cumulative counter. Partial coverage is visible; unknown is null, not zero; use integer quantities with bounds and explicit units. Only valid fixed target metrics display percentages; ongoing policies have no artificial completion bar.

## 5. API and security
Add versioned, GET-only account-scoped logical task collection, detail, event page and metrics DTOs under /api/v1/accounts/{id}/logical-tasks with opaque bounded cursors (timestamp + tie-breaker), allowlisted filters/status/operation/sort, limits and strict cross-account ownership validation. Add bounded aggregate multi-account summaries through existing authorized scope without arbitrary fanout. Include schema version, generated_at, last_observed_at, completeness, availability and pagination. Existing tasks/activity/receipts endpoints remain compatible; feature capability advertises version for old clients. BFF fixed allowlist, existing role/rate/size/cache controls; no mutation proxy. Client never posts telemetry or queries raw DB/logs. No credentials, cookies, tokens, HTML, raw exceptions, arbitrary config or opponent data; allowlisted typed fields, output size and retention quotas, safe export (CSV formula protection). No browser persistence of private data; bounded in-memory refresh when visible, backoff and stale indicators, cancel on scope/unmount; do not poll game. Existing reviewed stop/recovery controls call current authoritative APIs only. Test operator revocation, viewer role, origin, cross-account access, malformed IDs/cursors, oversized payloads and redaction.

## 6. UX
Web navigation becomes Tasks (legacy Activity route maps to Tasks), Apple-inspired responsive summary, tabs All/Active/Waiting/Needs attention/History, search account/operation, world and date/status filters, all/selected/one stable account IDs with player names. Summary counters derive from observed logical task states with unavailable accounts visible. Each card/compact row: task title, account/world, status, current stage, elapsed, relevant 2–4 metrics, last update, progress only with meaningful denominator; click or keyboard Enter opens detail (wide desktop split/detail, mobile full screen). Preserve selection and scroll without caching sensitive payloads.
Detail tabs: Activities (reverse chronology, grouped by run/day, expandable event details with route, quantities, timing, evidence); Statistics (unit-specific cards and charts from actual observations, labeled denominators and gaps); Configuration (approved read-only safe projection); Runs & recovery (attempt timeline, downtime, held/review state); Technical receipts (existing history linked, not mixed into user activity). World reports remain accessible separately. Error, empty, stale, unknown and partial states explicit. Manual refresh, page older, export filtered task history; no unsafe action on click. Accessible labels, keyboard focus, contrast, reduced motion, English/Russian web, existing native localization policy. Native Qt/Fluent Tasks page mirrors core hierarchy, filters, details and statistics through same controller API; native technical diagnostics remain separately available. Test compact layouts, dark/light, mobile, keyboard and old-backend compatibility.

## 7. Migration, retention, release
Stage schema on synthetic state, prove migration interruption, duplicate event, corrupt telemetry, disk full, reconnect and process crash behavior. Back up owner-only journals via existing protected procedures, never publish runtime state. Legacy engine tasks/receipts remain visible as limited-history entries if a trustworthy binding exists; otherwise show distinct unlinked receipts in technical history. No fake backfill. Propose configurable defaults (90 days event detail, 365 days rollups, 100,000 retained events per account, 16 KiB/event); capacity/load measurements and owner review before enabling; retention must not delete authoritative dispatch/recovery records. Rollups survive detail pruning, truncation visible. Add feature flag and capability negotiation; old clients continue working; rollback disables telemetry without touching ledgers or replaying. Roll out backend first with feature off, then dual-client compatibility, synthetic end-to-end and authorized live read-only validation; user acceptance for actual game effects. Version 0.2.0 only after exact green CI, documented owner gates, and approved rollout. No deployment on ordinary pushes.
